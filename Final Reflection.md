# Final Reflection

The AOCS Downlink Pipeline samples, estimates, and downlinks spacecraft attitude telemetry at 20 Hz across both cores of the ESP32. Core 1 runs the four-task real-time pipeline while Core 0 handles the observability plane through a web server or serial monitor. This project integrated concepts from across the semester: the HTTP/Wi-Fi stack from App 1, the button interrupt path and latency measurement approach from App 3, and the foundational architecture of App 5.

## The most valuable thing I learned

In a real-time system, correctness and predictability are entirely different properties, and predictability is the harder one by far. The queue makes this clear; data_q holds eight aocs_t structs. A functionally correct design would either size the queue large enough that it never fills or block the producer until there's room. However, both fail here. A massive queue turns a fast failure into a slow one feeding stale attitude data to the estimator. Conversely, blocking the producer means a slow consumer silently drags the sampler off its 20 Hz cadence turning a local bottleneck into a system wide timing failure.

Instead, I gave the producer a strict 5 ms send timeout one tenth of its period and on failure it evicts the oldest sample and loads the newest. The producer's worst-case execution time is now bounded by construction; it cannot be dragged off downstream. Dropping the oldest data is the correct policy for a control signal because the freshest reading is the only one that matters and a 400 ms old attitude sample is useless. Every drop gets logged so the system degrades in an obvious manner instead of silently dropping data. The other half of that lesson is that liveness has to be observable or it doesn't exist. Every Core 1 task increments its own heartbeat counter at the end of every loop, and Core 0 prints all four on a single line. If excluded, the system is running and every task is running look identical from the outside. That single line of telemetry became my primary debugging tool for the entire project.

## What was harder than expected

Measuring WCET was supposed to be straightforward, but it took three attempts to get numbers I actually trusted. My first iteration wrapped a wall clock timer around each whole task body producing a total utilization of 1.11 suggesting an non-feasible system. Meanwhile, heartbeats climbed evenly at 20 per second with the queue depth sitting at zero. When math and real world expectations disagree the measurement is likely wrong. 

Two things contaminated the data. First, ESP_LOGI blocks on the UART so the timer was measuring serial I/O rather than actual task execution. Second, IPC calls like xEventGroupSetBits and xTaskNotifyGive wake higher-priority tasks that preempt execution immediately by folding the preempting task's runtime into the caller's number. The consumer measured 19,860 µs at one point when its actual execution time was 8 µs. The takeaway is that on a preemptive kernel  a wall clock timer around a task body measures response time not execution time.

The corrected numbers came out to be 25, 8, 7, and 7 microseconds so 47 microseconds total which is 0.094 percent of the 50 ms window against a Liu and Layland bound of 0.757. However, a more critical outcome fell out of that same run: a single ESP_LOGI call takes 20,495 microseconds,which is 436 times the entire pipeline's compute time. Since the consumer and responder each log once per sample roughly 41 ms of every 50 ms window is spent on serial output while the actual work takes 47 µs. The system was I/O-limited. Adding that instrumentation also broke the boot sequence on every startup with an assert failed: xTaskGenericNotify tasks.c:5900 (xTaskToNotify). The coordinator was calling xTaskNotifyGive(responder_handle) before that handle had even been assigned because the responder was created last in app_main. That race condition had been there all along; however, original timing gave the scheduler enough slack to create all four tasks before the first rendezvous completed. Shifting the timing by a few microseconds made a latent bug show up on every single boot. 

## What I would do differently

I should have measured timing from the beginning instead of waiting until the end. I set priorities and queue depths by reasoning and measured to confirm. While the math held up knowing about the 20,495 µs logging penalty in week one would have changed how I structured serial output. I also should have noticed the heartbeats instead of only reporting them. Right now, heartbeats just print out and a human has to notice if one flats out. Detection without an automated response is only half a safety mechanism; a supervisor on Core 0 should catch a flatlined counter and trigger a safe state or task restart.
